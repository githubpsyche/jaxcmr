Templates

A template is a maintained notebook for a complete procedure: selecting observations, performing a calculation and saving interpretable results. Its parameters cell specifies one run. Changing those settings lets you reuse the procedure for another selection, model or experiment, or prepare many independent jobs without maintaining a separate procedure for each one.

These fourteen templates cover behavioral analysis, fitting, simulation, parameter exploration and pooled model comparison. Their defaults use the war-photo-recall experiment as a shared worked example. The saved figures and tables show that example; they are replaced when you execute a new run. Choose a task below, then download its notebook and required inputs.

The procedures connect through saved products:

  1. Describe responses. Analysis templates read observed or simulated response files, establish a pattern and expose discrepancies.
  2. Check a mechanism. Parameter shifting starts from saved baseline parameters and examines controlled interventions without refitting.
  3. Fit configured models. The single fitting template estimates parameters, saves fit records, optionally simulates, and compares configured benchmarks.
  4. Generate predictions. Simulation produces saved responses from any configured collection of fits.
  5. Compare results. Model comparison reads the saved fits and responses, relating likelihood, AIC, search variation and behavioral predictions.

The shared example compares ordinary CMR, source-only eCMR and broader eCMR. To inspect completed runs, use the supplied fits and responses. To change the scientific specification, configure the fitting or intervention procedure and pass its saved outputs to the analyses. The local instructions explain preparation and execution.

The experiment

In this experiment, Dupertuys and colleagues asked whether emotion changes both which pictures people remember and the order in which they remember them. Participants studied photographs relating to the war in Ukraine, then recalled them from memory. The final sample comprised 123 English-speaking adults selected for their reported concern about the war.

Each participant completed four rounds, each with two phases:

  1. Study the photographs. A list contained twelve target photographs, plus an extra “buffer” photograph at each end. Each image appeared for six seconds, followed by a three-second blank screen.
  2. Recall the photographs. Immediately after the list, participants typed short descriptions of as many photographs as they could remember, in any order. They then continued to the next study-and-recall round.

Researchers later scored the typed responses by matching descriptions to photograph identities, retaining the order in which the pictures were recalled.

The lists differed in their emotional composition. Emotional photographs were rated as more negative and more arousing; neutral photographs were the less negative, less arousing comparison images from the same war-related set. Every participant encountered all three conditions:

List condition Target photographs in each list Lists per participant
Mixed 6 emotional and 6 neutral 2
Pure emotional 12 emotional 1
Pure neutral 12 neutral 1

List order was counterbalanced across participants, and target-picture order was randomized within each list. Targets were not repeated across a participant’s four lists.

Mixed lists let us compare emotional and neutral recall within the same list. Pure lists let us ask how that difference changes when the two types of picture are studied separately. Recording recall order also lets us examine memory search: for example, whether one recalled picture tends to be followed by a picture studied nearby in time, or by a picture with similar meaning.

The data used in the templates

The supplied file contains 492 list records: 246 mixed, 123 pure-emotional and 123 pure-neutral. Photographs are represented by item identifiers, and recall responses by scored sequences. Buffer photographs are excluded, so the study positions used in these templates refer to the twelve target photographs. One pure-emotional record contains eleven valid target items and a padded slot; the fixed-length analyses identify and exclude that record.

Field Meaning in these procedures
subject Participant identifier, retained when simulating.
list_type Whole-list condition: 1 = mixed, 2 = pure emotional, 3 = pure neutral.
pres_itemnos Studied item codes within a trial; zero is a padded slot.
pres_itemids Global picture identifiers used to align the distance matrix and categories.
recalls One-based study positions of recalled items; zero is an unused response slot.
valence Category at each study position: −1 = emotional, 0 = neutral. Check valid study items before counting categories.

Study positions and item identities are different: a recall code of 3 points to the third study slot, whose global picture identifier is found in pres_itemids. The supplied distance matrix is indexed by global identifier minus one. Its missing entries are outside the within-list comparisons used here; every within-list pair required by the semantic examples has a finite distance.

Selections are made in notebook cells and leave the source file unchanged:

  • Fitting and pooled model comparison: all 492 lists and all conditions.
  • SPC, PNR, stopping and temporal organization: the 491 complete twelve-item lists. Each notebook explicitly reports the one excluded padded list.
  • Semantic organization: the 246 mixed lists and the supplied distance matrix.
  • Category recall rate: all conditions, with valid-item denominators.
  • Category SPC and category-CRP: mixed lists by default.

Plots summarize each participant’s selected lists before averaging across participants. Error bars describe bootstrap intervals for those participant summaries. Some bins have no variation or no defined values, so the current plotters can report that a bootstrap interval is undefined; this does not turn an unavailable category or transition into a zero-valued observation.

Run in Colab

Choose Open in Colab beside a chapter’s contents list. Sign in to Google, then choose Runtime → Run all. For the notebook opened from this repository, Colab may ask you to confirm Run anyway. A standard CPU runtime is enough.

The setup cell installs JAXCMR from GitHub’s main branch and downloads only that notebook’s supplied inputs, checking their hashes. This route works before the PyPI release. Matching files are reused when setup runs again; a conflicting file is preserved and reported. If you change a path to your own input, upload that file through Colab’s Files pane and keep the path consistent with the parameters cell.

If Colab requests a restart after installation, choose Runtime → Restart session, then Run all again. The first raw cell contains Quarto page metadata; Colab labels it “Unsupported Cell Type”, but skips it when running the code cells.

Results are written under the notebook’s output_dir (for SPC, results/spc/spc.png). In the Files pane, open that folder and use the file’s menu to Download the results. Download anything you want to keep before Colab deletes the temporary runtime. Use File → Download → Download .ipynb to retain an executed notebook, or Copy to Drive if you want a saved working copy. For local installation, use the homepage command.

Colab links and setup follow main as it changes. The rendered chapter and download are refreshed when the book is rebuilt. Analysis notebooks fetch saved model responses; they do not fit or simulate.

From a template to a run

Save downloaded notebooks in your working folder, beside data/. Open the folder in your notebook editor, select its Python environment, edit the parameters cell and run the notebook from top to bottom. Relative paths follow the project-directory rules below. Give independent runs distinct output folders or run names so their results do not overwrite one another.

Paths and working directories

The project_root parameter selects the base for all relative input and output paths:

Setting or execution context Base directory
An explicit project_root That directory; a relative value uses the kernel’s starting directory.
Local checkout, project_root=None The enclosing Git root, found by the existing find_project_root() helper.
Standalone folder, project_root=None The kernel’s working directory.
Colab, project_root=None The runtime’s working directory.

The notebook reports the chosen directory. Running from templates/ or a nested prepared-job directory inside a checkout uses the same project inputs and outputs. When the kernel starts outside the project, supply project_root explicitly. The root belongs to your research project; it is not the installed JAXCMR package directory.

Absolute paths remain absolute, and ~ expands to your home directory. On Windows, "C:/Users/Alex/my-study" or r"C:\Users\Alex\my-study" works; avoid a partially specified drive path such as "C:my-study". UNC paths are supported on Windows. Relative defaults such as "data/Dupertuys2026.h5" work on both platforms. An absolute path from another computer must be updated there.

Colab downloads recognized relative example names into this same base. Custom files remain your responsibility; selecting an absolute custom path does not download an example over it. Path resolution happens after parameter injection and does not change the process’s working directory.

Saved products and regeneration

Copy the fit_paths printed by fitting into simulation, then supply the printed simulation_paths to model comparison or their values as analysis data_paths. The defaults continue to use the supplied examples until you replace them. For example, a one-model simulation job can use:

fit_paths = {"CMR": "results/fits/Dupertuys2026_CMR_demo_best_of_3.json"}

output_dir supplies default locations, but explicit directory settings take precedence:

Procedure Directory precedence
Fitting target_directory or output_dir supplies the product root; explicit fit_dir, simulation_dir and figure_dir override their defaults.
Simulation Explicit simulation_dir and figure_dir override output_dir. The example sets simulation_dir="results/simulations".
Parameter shifting, model comparison and analyses Explicit figure_dir overrides its default; summary tables use output_dir.

Give independent jobs distinct names or directories for every product they write. redo_fits=False reuses a matching existing fit; a missing fit is still computed and an incompatible record is reported. redo_sims=False permits matching response reuse; when predictions are requested, missing or stale responses are regenerated. Fitting is fit-only when both redo_sims and redo_figures are false. figure_str="" disables figure saving, but does not disable summary CSVs or provenance capture.

Settings are ordinary values: paths, numbers, lists, dictionaries and import names. Imports, trial masks and model construction happen afterward, using the effective values. The fitting template can select a model and its components, objective, fitted parameters, participant subset and displayed analyses. Analysis templates expose their trial selections and measure-specific settings. Their inputs are saved response files; preparing or running an analysis does not generate missing simulations.

Ordinary imports occupy their own cell after the optional Colab bootstrap. Derived paths, loading and calculations follow the injected parameters. figure_str="" displays figures without saving them; a nonempty name saves under figure_dir. The defaults provide explicit names for the worked examples. Subject-level CSV summaries use output_dir.

The analysis controls include repeated-item capacity (size), stopping mode, condition queries, category fields and labels, and plot limits. Category recall also accepts configured paired contrasts and contrasts of contrasts. Select these for the question being asked; the defaults leave the optional tests empty.

You can also supply settings externally. Quarto and Papermill use the same tagged cell. An override replaces a whole top-level value: to change one model, supply the complete model_configs dictionary for that work unit. Use fit_alg_path and fit_hyperparams to select and configure the optimizer. Analysis templates use data_paths and data_labels for a collection; an explicit data_path retains single-dataset use. Their condition queries are applied to each input.

Execute a report with Quarto

With Quarto installed, you can execute a notebook with overrides and render its results to HTML. Python parameter injection uses Papermill, which the repository’s default uv sync already installs. For this example, run from the repository root and select the environment for Quarto using the command for your shell:

  • macOS / Linux
  • Windows PowerShell
export QUARTO_PYTHON="$(uv run python -c 'import sys; print(sys.executable)')"
$env:QUARTO_PYTHON = (uv run python -c "import sys; print(sys.executable)")

Then run the same command on either platform:

quarto render templates/pnr.ipynb --execute -P query_recall_position:2 -P output_dir:results/pnr-third --output pnr-third.html

Quarto normally executes from the notebook’s directory; the template’s root lookup handles that. An injected project_root also works for notebooks prepared outside the project. The book build itself does not execute notebooks.

Output positions are zero-based, so 2 means the third response. Use --execute-params settings.yml for dictionaries or longer selections. The explicit --execute runs the notebook; rendering an .ipynb without it normally displays its stored results. The book itself displays stored examples.

Prepare independent jobs with Papermill

For a cluster batch, it can be useful to inspect the complete set of jobs before executing any of them. Papermill’s prepare_only=True creates a configured notebook for each job. From the repository root, the following Python cell prepares two fitting runs that differ only in optimization seed and output folder:

Prepare two fitting jobs without running them 
from pathlib import Path
from copy import deepcopy
import nbformat
import papermill as pm

source = nbformat.read("templates/fitting.ipynb", as_version=4)
defaults = {}
parameter_cell = next(cell for cell in source.cells
                      if "parameters" in cell.metadata.get("tags", []))
# Evaluate only the parameter assignments, not the fitting procedure.
exec(parameter_cell.source, defaults)

jobs = Path("analyses/rendered")
jobs.mkdir(parents=True, exist_ok=True)
for seed in [0, 1]:
    configs = deepcopy(defaults["model_configs"])
    for config in configs.values():
        config["seed"] = seed
    path = jobs / f"fitting_seed_{seed}.ipynb"
    prepared = pm.execute_notebook(
        "templates/fitting.ipynb", str(path),
        parameters={"model_configs": configs, "output_dir": f"results/fitting-seed-{seed}"},
        prepare_only=True,
    )
    # Stored example results are not results from this new job.
    for cell in prepared.cells:
        if cell.cell_type == "code":
            cell.outputs = []
            cell.execution_count = None
    nbformat.write(prepared, path)

To prepare one model per job, pass a one-entry model_configs dictionary. Preserve the project’s chosen job boundaries: a model collection does not require running every model in each scheduled job. Inspect the injected settings in each notebook. Execute one from the working folder with:

uv run papermill analyses/rendered/fitting_seed_0.ipynb analyses/rendered/fitting_seed_0.ipynb --cwd .

The same prepared notebooks can be transferred with their inputs and run as separate Slurm jobs, using the project folder as the working directory. This keeps the prepared paths portable: set --cwd to the destination project folder, or inject its project_root when executing. Do not inject a local machine’s absolute root into jobs intended for a different machine. This matches the remote-cluster workflow: maintain a procedure, prepare concrete work units, then schedule their execution. Preparing jobs does not fit a model; rendering HTML is a separate presentation step.

For participant jobs, the fitting template uses pooled=False and subject_indices=[i], where i indexes the sorted participant IDs. Simulation and parameter exploration can instead vary seeds or parameter values. Choose the work unit around the scientific question and keep its inputs and outputs explicit. A fit-only job sets both redo_sims and redo_figures to False; later simulation can use its saved result.

Modeling procedures

The example collection estimates nine continuous CMR parameters and ten for each eCMR variant, using the same observations and termination-excluded likelihood. The two eCMR specifications differ in whether emotional modulation also affects temporal association learning. The default simulator conditions on observed recall counts. Recall length, stopping distributions and pure-list category totals therefore are imposed; mixed-list category allocation and recall organization can vary.

Simulation and parameter shifting start from the supplied fits without optimization. The latter includes encoding-drift sweeps and a separate controlled temporal-emotional-modulation switch. Model comparison consumes the saved fits and responses. Its results describe pooled solutions, not independent participant estimates. Each procedure remains configurable for other inputs, models and scientific questions.

Adapting a procedure

Start by changing the settings cell: input paths, trial selection, parameters and output folder. Check the meanings of item codes, participant identifiers, categories and response padding before interpreting results. Retain the same selection for comparisons that are intended to address the same observations.
