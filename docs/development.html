Development

For changes to JAXCMR itself, use the optional repository checkout described in Local setup with VS Code. Run these commands from the repository root.

Prepare the environment

uv sync --locked --extra test --group reader

This installs the editable library, development tools, and notebook-test dependencies in one environment. The test extra adds only pytest. The default dev group includes the build and notebook tools for optional local checks; library CI does not install that group. Optional groups remain available: --group embeddings for sentence-transformers, --group profiling for line-profiler, and --extra experimental for the experimental Numba helper.

Edit and check notebooks

Edit original notebooks in templates/ or guide/, preserving useful saved outputs. Their short installation cells run only in Colab. Local and Slurm kernels use the environment the reader selected.

While changing executable code, run the affected cases:

uv run --no-sync python guide/tools/check_notebooks.py --select cat_recall_rate

Run all 17 cases before publishing changes to shared setup, example inputs, or library functionality:

uv run --no-sync python guide/tools/check_notebooks.py

The runner uses nbmake and pytest with two workers in the current environment. It executes temporary notebook copies, reduces workloads for testing, and reopens saved results in a separate process. The spreadsheet case uses synthetic inputs. Original notebook parameters and outputs are never rewritten. --jobs 1 runs serially; --platform windows selects the representative Windows cases. The report identifies the environment used and separates preparation and execution time.

Notebook execution is a local maintainer tool; GitHub Actions does not run notebooks or tests that execute notebook cells.

For prose and saved-output changes, render and check the website; execution is needed when calculations change. Adding a published notebook also requires adding its bounded case to the notebook test runner.

Test the library and installation

uv run --no-sync python -m pytest tests -m "not audit" \
  --ignore=tests/test_distribution.py \
  --ignore=tests/test_reader_checks.py \
  --ignore=tests/test_template_adaptation.py \
  --ignore=tests/test_documentation.py

While editing, select the relevant test file instead of repeating the full suite. Routine checks include scientific calculations, public validation, and complete modeling workflows. Three additional audit cases check compilation reuse in prepared losses and the gradient and evolutionary fitters:

uv run --no-sync python -m pytest tests -m audit

Run these checks before releases and when changing loss preparation or fitting compilation. Unfiltered pytest still includes the audit, notebook-related and distribution tests. Routine CI runs only the library selection above, against a normal installation made with python -m pip install ".[test]". It uses python -P -m pytest so Python does not import the adjacent checkout in place of the installed package. This tests dependency resolution from the package requirements; local editable development still uses uv.lock.

The optional local distribution tests build a wheel and source archive, rebuild from the archive, and install into a clean environment outside the checkout. They check the installed README example and offline preparation of all bundled inputs. Library tests cover input conflicts and custom paths; notebook checks exercise the current published notebooks. This separate installation check needs internet access for dependencies and does not run in CI:

uv run --no-sync python -m pytest tests/test_distribution.py

New tests should catch incorrect behavior using independently established numerical answers or supported workflows. Put short derivations beside analytic expectations; identify historical regression values as such. Check observable results rather than private object identities, and use small doubles only at necessary boundaries. Required checks must not silently skip because private data is unavailable. When an assertion’s strength is uncertain, temporarily introduce the suspected fault and confirm that it fails for the intended reason. Keep the behavioral assertion, without adding a permanent test that reruns another test. Test our notebook preparation and result validation directly; rely on nbmake and pytest for notebook execution and failure reporting.

See the test fixtures and CI workflow.

Keep validation proportionate

Check inexpensive structural requirements where data enter an operation, especially when broadcasting or indexing could silently change observation or participant assignments. Keep value-dependent checks outside compiled calculations. Numerical analysis functions remain JIT-compatible and require valid inputs; full distance preflight checking remains optional. Test demonstrated failures through public operations without duplicating every check across wrappers and kernels.

Maintain the supplied examples

The eleven selected files under data/ and their fit methods document are the authoritative inputs. Packaging explicitly includes them; other research data and results remain excluded. The library’s fetch_inputs(paths, base_dir=...) copies only requested bundled examples, reuses matching files, and preserves conflicts and custom paths. An explicit revision= downloads reference bytes from GitHub on each call, including when checking an existing file. The default bundled route works offline. Neither route requires maintaining content hashes.

When changing a supplied input, update its methods or source notes as needed. The filenames are listed in jaxcmr/examples.py; adding an example also requires including it in the package configuration. jaxcmr.examples.fetch_inputs is the current import; jaxcmr.colab.fetch_inputs remains compatible with older notebooks. Reinstall the editable package to refresh its bundled resources, then run the notebook and distribution checks:

uv sync --locked --extra test --group reader --reinstall-package jaxcmr

The website stages downloads from those same authoritative files. Notebook explanation and analysis changes can be published without a package release. Library and bundled data changes require readers to update their installation; the Git installation route does not require a PyPI release.

Saved settings and older notebooks

Fit and simulation records describe the models, parameters, input paths, selected rows and run settings. Reuse checks compare these settings; fitting also recalculates the saved objective. Changes to data or code at an existing location require rerunning the affected calculations. Keep the input files and notebook with results you intend to reproduce.

Automatic source capture has been removed. Update older notebook copies that import capture_notebook or file_sha256 from jaxcmr.provenance; those functions and the provenance_dir, provenance_source_paths and notebook_source controls are no longer used. Existing records can retain obsolete digest fields, which no longer govern reuse.

Build and preview the website

Use Quarto 1.11.9, available on your command path, matching CI:

bash build-docs.sh
uv run --no-sync python guide/tools/check_site.py docs
uv run --no-sync python -m http.server 8786 --bind 127.0.0.1 --directory docs

Open http://127.0.0.1:8786/. The build stages notebook pages and byte-for-byte source downloads before rendering, without executing notebooks. It removes retired generated files and protects source directories. Do not edit guide/templates/, guide/downloads/, or rendered HTML. Rebuild after edits; the file server serves the rebuilt pages.

Colab links and installation commands follow main. A local preview’s download includes local changes; its Colab button still opens the last pushed notebook.

Publication and release handover

The routine Checks and website workflow runs on pull requests targeting main, pushes to main, and manual requests. It has four testing/build jobs:

  • Library tests (Linux, macOS and Windows): one shared job definition runs separately on all three platforms, using Python 3.12 and CPU execution. Each installs JAXCMR normally with pip install ".[test]", then runs the same library tests and exclusions. A failure on one platform does not cancel the other platform runs.
  • Website: a Quarto build, download/link checks, and a downloadable preview artifact.

Feature-branch pushes do not also trigger a second run for an open pull request. Open a draft pull request to get automatic checks while working on a branch. There is no file-based change selection; each routine run performs the four jobs.

CI does not execute notebooks, test notebook cells or run the separate distribution rehearsal. The website build renders saved outputs and verifies download copies and links without executing notebooks. There is no additional platform-compatibility workflow. Notebook and distribution tools remain available for local use.

After the one-time Pages handover below, pushing documentation sources to main builds and publishes the website automatically. Local rendering remains useful for previewing changes; publishing no longer depends on committing generated HTML. Pull requests produce downloadable previews without publishing them.

Deployment waits for the Linux, macOS, Windows and website jobs to pass, then publishes the website artifact from that same run. It also checks that its commit is still the latest main. A manual workflow run can publish main through the same checks. No additional repository variable is required.

For the one-time handover:

  1. Push the reviewed workflow and its supporting source changes. In repository Settings → Pages → Build and deployment, change Source from Deploy from a branch to GitHub Actions.
  2. Run or rerun Checks and website for the current main commit, and verify that the library, website and deployment jobs all succeed. If branch rules require the previous job names, update those required checks when adopting this workflow.
  3. Verify the public Setup pages, notebook downloads, example inputs, and Colab links. Check changed notebooks in hosted Colab separately, including a fresh runtime and your own input/output files.
  4. After the replacement deployment is verified, remove docs/ from Git tracking and add /docs/ to .gitignore, keeping local rendered files available for previews.

Until the handover is completed, retain the tracked docs/ site and the existing branch-based publishing configuration. If the replacement deployment fails, the previous public site remains available; fix the failure and rerun the workflow.

PyPI publication remains separate. Before publishing a release, review the library and website checks, run the compilation audits, and select any additional local notebook or distribution checks needed for the changes being released. After publication, verify installation from PyPI in a clean environment before changing the short installation commands. A PyPI release is not required for ordinary notebook improvements or Git-based distribution.
