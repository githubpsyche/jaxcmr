Development

For changes to JAXCMR itself, use the optional repository checkout described in Local setup with VS Code. Run these commands from the repository root.

Prepare the environment

uv sync --locked --extra test --group reader

This installs the editable library, development tools, and notebook-test dependencies in one environment. The test extra adds only pytest. The default dev group includes the build and notebook tools for optional local checks; library CI does not install that group. Optional groups remain available: --group embeddings for sentence-transformers, --group profiling for line-profiler, and --extra experimental for the experimental Numba helper.

Edit and check notebooks

Edit original notebooks in templates/ or guide/, preserving useful saved outputs. Their short installation cells run only in Colab. Local and Slurm kernels use the environment the reader selected.

While changing executable code, run the affected cases:

uv run --no-sync python guide/tools/check_notebooks.py --select cat_recall_rate

Run all 17 cases before publishing changes to shared setup, example inputs, or library functionality:

uv run --no-sync python guide/tools/check_notebooks.py

The runner uses nbmake and pytest with two workers in the current environment. It executes temporary notebook copies, reduces workloads for testing, and reopens saved results in a separate process. The spreadsheet case uses synthetic inputs. Original notebook parameters and outputs are never rewritten. --jobs 1 runs serially; --platform windows selects the representative Windows cases. The report identifies the environment used and separates preparation and execution time.

Notebook execution is a local maintainer tool; GitHub Actions does not run notebooks or tests that execute notebook cells.

For prose and saved-output changes, render and check the website; execution is needed when calculations change. Adding a published notebook also requires adding its bounded case to the notebook test runner.

Test the library and installation

uv run --no-sync python -m pytest tests -m "not audit" \
  --ignore=tests/test_distribution.py \
  --ignore=tests/test_reader_checks.py \
  --ignore=tests/test_template_adaptation.py \
  --ignore=tests/test_documentation.py

While editing, select the relevant test file instead of repeating the full suite. Routine checks include scientific calculations, public validation, and complete modeling workflows. Two additional audit cases check compilation reuse across prepared participant selections in the experimental gradient and evolutionary CMR fitters:

uv run --no-sync python -m pytest tests -m audit

Run these checks before releases and when changing experimental CMR preparation or fitting compilation.

Ordinary fitting uses LossFn with explicit trial indices. OptimizedCMR’s prepared observations and selection cache belong in jaxcmr/experimental/optimized_cmr.py; its fitting adapters belong in jaxcmr/experimental/optimized_cmr_fitting.py. Keep their types and preparation methods out of the ordinary model/loss protocols. The ordinary optimizer routines accept numerical objectives and are shared without importing the experimental implementation. Unfiltered pytest still includes the audit, notebook-related and distribution tests. Routine CI runs only the library selection above, against a normal installation made with python -m pip install ".[test]". It uses python -P -m pytest so Python does not import the adjacent checkout in place of the installed package. This tests dependency resolution from the package requirements; local editable development still uses uv.lock.

The optional local distribution tests build a wheel and source archive, rebuild from the archive, and install into a clean environment outside the checkout. They check the installed README example and offline preparation of all bundled inputs. Library tests cover input conflicts and custom paths; notebook checks exercise the current published notebooks. This separate installation check needs internet access for dependencies and does not run in CI:

uv run --no-sync python -m pytest tests/test_distribution.py

New tests should catch incorrect behavior using independently established numerical answers or supported workflows. Put short derivations beside analytic expectations; identify historical regression values as such. Check observable results rather than private object identities, and use small doubles only at necessary boundaries. Required checks must not silently skip because private data is unavailable. When an assertion’s strength is uncertain, temporarily introduce the suspected fault and confirm that it fails for the intended reason. Keep the behavioral assertion, without adding a permanent test that reruns another test. Test our notebook preparation and result validation directly; rely on nbmake and pytest for notebook execution and failure reporting.

See the test fixtures and CI workflow.

Where shared operations live

Use jaxcmr.dataset for dataset construction, trial and recall selections, and participant grouping. jaxcmr.repetition handles repeated items and shuffled controls; jaxcmr.math contains numerical primitives. Shared figure creation and the save_figure interface live in jaxcmr.plotting; analysis-specific plots stay with their analyses.

jaxcmr.analyses._study_positions is private to the measurement analyses. It computes presentation-inclusion masks and recall indicators; public analyses own aggregation, weighting and interpretation. Keep measurement availability separate from recall classification, including when an item appears repeatedly. The operations in repetition.py return position indices for individual items; the private analysis helpers return Boolean matrices over trials and positions.

The jaxcmr.helpers reference groups file, path, and configuration utilities implemented in jaxcmr/helpers.py. Import these functions directly from jaxcmr.helpers. Dataset operations belong in jaxcmr.dataset; repeated-item operations belong in jaxcmr.repetition.

helpers.load_hdf5_arrays reads named arrays without requiring recall fields. Use load_data for a RecallDataset, or the generic reader for other observations such as temporal judgments. Both read the same transposed /data layout written by save_dict_to_hdf5. For non-recall data, apply limit_to_first_subjects explicitly when participant selection is needed.

All project-path functions return Path. find_project_root requires an enclosing marker; resolve_project_root supplies the documented current-directory fallback. Use str(path) where another interface requires a string, such as sys.path.

jaxcmr.plotting.save_figure requires figure= and saves without displaying. Call plt.show() explicitly to display figures. For display-only output, call figure.tight_layout() and plt.show() without saving. The saving implementation lives alongside the other figure operations in jaxcmr/plotting.py.

The package-level jaxcmr.make_dataset and jaxcmr.load_data entry points remain available. RecallDataset and shared annotations live in jaxcmr.typing. jaxcmr.fitting.parameters.bound_params clips parameter columns to their bounds; its existing re-export from summarize remains. The unused load_opt_params loader and OptimizationParameters type have been removed. Read JSON settings in the caller when needed; this change introduces no replacement configuration format. summarize owns descriptive parameter tables and statistical comparisons.

Declare type aliases with the Python 3.12 type statement. Use Parameters for a mapping containing one set of scalar model settings; participant columns and optimizer populations retain their explicitly shaped array annotations.

Keep validation proportionate

Treat annotations and documented preconditions as caller responsibilities. This includes array shapes, matching labels and masks, supported model inputs, and valid option values. Do not add guards or negative tests solely to police those requirements. Explain them beside the operation; use precise annotations where practical. Broad annotations such as Any do not justify extra guards.

Keep numerical functions focused on their calculations. Document valid input shapes, codes and configuration; rely on ordinary array errors instead of repeating shape, dtype and key checks in kernels. Valid inputs must compose with JAX transformations, including numerical parameters passed through vmap.

Preparation is not an exception: ordinary fitting and analysis calls trust their documented inputs. Keep normalization, participant alignment and observation preparation themselves. Do not add equivalent checks through a wrapper or a strict zip over caller-supplied collections.

Clients own input validity and saved-fit reuse, including checks they choose to perform explicitly. Do not add standalone validators or move their implementation into notebooks. Document the required inputs and reuse decisions beside the calls.

Keep external-file protections, internal invariants, and failures encountered during computation (including nonconvergence, precision collapse and undefined AICc). Scientific eligibility masks, padding and missing-observation rules remain part of the calculation. Preserve supported numerical tests; remove only the invalid-call portions of tests that also exercise useful behavior.

Maintain the supplied examples

The eleven selected files under data/ and their fit methods document are the authoritative inputs. Packaging explicitly includes them; other research data and results remain excluded. The library’s copy_example_inputs(paths, base_dir=...) copies only requested bundled examples, reuses matching files, and preserves conflicts and custom paths. Copying works offline; the examples come from the installed package. It does not check whether custom inputs exist or are ready to load.

When changing a supplied input, update its methods or source notes as needed. The filenames are listed in jaxcmr/examples.py; adding an example also requires including it in the package configuration. Import copy_example_inputs from jaxcmr.examples. Reinstall the editable package to refresh its bundled resources, then run the notebook and distribution checks:

uv sync --locked --extra test --group reader --reinstall-package jaxcmr

The website stages downloads from those same authoritative files. Notebook explanation and analysis changes can be published without a package release. Library and bundled data changes require readers to update their installation; the Git installation route does not require a PyPI release.

Saved settings and older notebooks

Fit and simulation records describe the models, parameters, input paths, selected rows and run settings. Reuse checks compare these settings; fitting also recalculates the saved objective. Changes to data or code at an existing location require rerunning the affected calculations. Keep the input files and notebook with results you intend to reproduce.

Automatic source capture and the former jaxcmr.provenance module have been removed. Use load_matching_simulation from jaxcmr.simulation to load responses whose saved settings match a requested run. Keep regeneration decisions in the caller; the settings comparison is private. Update older notebook copies that import capture_notebook or file_sha256 from jaxcmr.provenance; those functions and the provenance_dir, provenance_source_paths and notebook_source controls are no longer used. Existing records can retain obsolete digest fields, which no longer govern reuse.

Build and preview the website

Use Quarto 1.11.9, available on your command path, matching CI:

uv sync --locked --group docs
bash build-docs.sh
uv run --no-sync python guide/tools/check_site.py docs
uv run --no-sync python -m http.server 8786 --bind 127.0.0.1 --directory docs

Open http://127.0.0.1:8786/. The build stages notebook pages and byte-for-byte source downloads before rendering, without executing notebooks. It removes retired generated files and protects source directories. Do not edit guide/templates/, guide/downloads/, or rendered HTML. Rebuild after edits; the file server serves the rebuilt pages.

Colab links and installation commands follow main. A local preview’s download includes local changes; its Colab button still opens the last pushed notebook.

Maintain API reference pages

API reference pages, including plotting, simulation and shared types, use the module docstring as their introduction. Each then shows grouped summary tables followed by the complete API entries.

Maintain the headings, membership and order in one Quartodoc configuration per module, such as guide/reference/_plotting.yml or _typing.yml. The build uses those groups for the tables and entry order. Quarto generates the page outline from the resulting headings, with the function links under API entries. Do not edit the generated content or duplicate the lists in the page’s .qmd file.

Edit explanations, parameter meanings and return descriptions in the Python docstrings. Use NumPy-style Parameters and Returns/Yields sections for public operations where applicable; existing Google-style sections remain supported. The build reads source text without executing the documented functions.

Install the docs dependency group and use Quarto 1.11.9. To rebuild one page, run this from guide/:

quarto render reference/simulation.qmd

That command regenerates only the simulation reference and skips notebook staging. Run it again after changing a Python docstring or the grouping YAML; a running preview does not guarantee detection of those external inputs. Use quarto render reference to rebuild all reference pages with one preparation step after a shared layout change. quarto render prepares all references and downloads before building the full site. Running uv run --no-sync python prepare.py directly also prepares all inputs without rendering. No LLM is involved in any of these commands.

Shared page settings live in guide/reference/_metadata.yml, styling in reference.css, and renderer extensions in guide/_api_renderer.py. Quartodoc’s single-page builder and Griffe supply source parsing, groups and API tables; our renderer places the overview and index before the entries and adjusts their presentation. The preparation step adapts Python 3.12 type aliases for Quartodoc 0.11; their definitions and descriptions still come from source. The renderer labels protocols as interfaces and includes field descriptions for typed dictionaries. Generated files in guide/reference/_generated/ are ignored build inputs. Review the affected page after a documentation edit, and all reference pages after a shared layout change. Existing website checks cover local links and notebook downloads.

Publication and release handover

The routine Checks and website workflow runs on pull requests targeting main, pushes to main, and manual requests. It has four testing/build jobs:

  • Library tests (Linux, macOS and Windows): one shared job definition runs separately on all three platforms, using Python 3.12 and CPU execution. Each installs JAXCMR normally with pip install ".[test]", then runs the same library tests and exclusions. A failure on one platform does not cancel the other platform runs.
  • Website: a Quarto build, download/link checks, and a downloadable preview artifact.

Feature-branch pushes do not also trigger a second run for an open pull request. Open a draft pull request to get automatic checks while working on a branch. There is no file-based change selection; each routine run performs the four jobs.

CI does not execute notebooks, test notebook cells or run the separate distribution rehearsal. The website build renders saved outputs and verifies download copies and links without executing notebooks. There is no additional platform-compatibility workflow. Notebook and distribution tools remain available for local use.

After the one-time Pages handover below, pushing documentation sources to main builds and publishes the website automatically. Local rendering remains useful for previewing changes; publishing no longer depends on committing generated HTML. Pull requests produce downloadable previews without publishing them.

Deployment waits for the Linux, macOS, Windows and website jobs to pass, then publishes the website artifact from that same run. It also checks that its commit is still the latest main. A manual workflow run can publish main through the same checks. No additional repository variable is required.

For the one-time handover:

  1. Push the reviewed workflow and its supporting source changes. In repository Settings → Pages → Build and deployment, change Source from Deploy from a branch to GitHub Actions.
  2. Run or rerun Checks and website for the current main commit, and verify that the library, website and deployment jobs all succeed. If branch rules require the previous job names, update those required checks when adopting this workflow.
  3. Verify the public Setup pages, notebook downloads, example inputs, and Colab links. Check changed notebooks in hosted Colab separately, including a fresh runtime and your own input/output files.
  4. After the replacement deployment is verified, remove docs/ from Git tracking and add /docs/ to .gitignore, keeping local rendered files available for previews.

Until the handover is completed, retain the tracked docs/ site and the existing branch-based publishing configuration. If the replacement deployment fails, the previous public site remains available; fix the failure and rerun the workflow.

PyPI publication remains separate. Before publishing a release, review the library and website checks, run the compilation audits, and select any additional local notebook or distribution checks needed for the changes being released. After publication, verify installation from PyPI in a clean environment before changing the short installation commands. A PyPI release is not required for ordinary notebook improvements or Git-based distribution.

Known padded-list plotting issue

A dataset can store a two-item list in four presentation columns, with trailing zeros and listLength=2. spc returns four positions, while plot_spc currently builds a two-position axis from find_max_list_length, causing a dimension mismatch. This needs a separate plotting correction that aligns displayed positions with the calculated scores. find_max_list_length continues to report declared study lengths; changing it to return storage width would change its meaning. The dataset refactor does not alter this behavior.

Analysis modules and reference pages

Keep trial calculations, participant summaries and specialized plotters together when they describe the same measure. analyses.statistics owns finite-pair comparisons and bootstrap intervals. Shared study-position and transition array operations are internal; eligibility and history decisions remain visible in the analysis that owns them. Existing repetition tabulators support research subclasses, so preserve their methods when consolidating calculations.

The analysis reference groups the public modules by measure. Provisional measures have a separate index. Each module page uses the existing _analyses-*.yml or _experimental-*.yml group definition and the source docstrings. There is no additional generator.

For new scientific conventions, retain a counted example with its denominator. Rerun affected summaries when changing an estimator; do not treat preserved notebook outputs or saved research reports as regenerated evidence. Item-recall deduplication, repeated-presentation credit, pooled RPL bins and finite-pair statistics can change those summaries without requiring a model refit.
