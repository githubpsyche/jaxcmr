Remote setup with VS Code on a Slurm cluster

Use VS Code to work with notebooks and files on a Slurm cluster. Your computer displays the editor; the cluster stores your research project and runs Python. You do not need Python installed locally.

A cluster is a collection of shared computers. Clusters provide resources for work that exceeds your computer’s capacity and for running independent jobs simultaneously. This guide prepares an interactive workspace for developing and checking your work. For unattended execution and multiple independent runs, continue with Run batches of notebooks unattended on Slurm. Requesting more CPUs does not automatically make a calculation faster.

Where the work happens

Location Role
Your computer Displays VS Code and connects to the cluster
Login node Provides access to files and lets you prepare and submit work
Compute node Runs calculations using resources allocated by Slurm

A node is a computer in the cluster. Login nodes are shared access points, so substantial calculations belong on compute nodes. Slurm manages access: you request resources, and it starts your work when suitable resources are available.

Before you begin

You need a cluster account and the following details from your institution:

Information What you need it for
Login address and username Connecting to the cluster
Authentication requirements Any VPN, password, authentication app, or SSH key needed to sign in
Project storage location Keeping code, installed software, and results
Slurm account Selecting the research allocation charged for computing use
CPU partition Selecting a permitted group of compute nodes
Supported VS Code access method Connecting the editor to allocated resources

Your login username and Slurm account may differ.

Prefer your institution’s managed VS Code service if it provides one. Use its connection and allocation instructions, then follow the project, environment, and notebook steps below in that workspace.

The SSH route below requires your institution to support all three of these:

  • VS Code and software installation on the login node.
  • SSH access through the login node to a compute node assigned to you, including any required key setup.
  • Running the connected VS Code processes inside your Slurm allocation. A matching computer name alone does not establish this; the cluster must support this connection method.

These are cluster settings to confirm before starting. For example, Harvard documents distinct SSH and tunnel routes. If direct SSH is unsupported, use the institution’s managed service or documented tunnel procedure.

Choose storage for your work

Use a project location accessible from both login and compute nodes. Your institution should identify where to keep software environments, research inputs, and results.

Storage names vary, but the distinctions matter:

Storage characteristic What it means for your work
Persistent shared storage Files remain available across allocations; check whether it is backed up.
Scratch storage Intended for working files; it may have an automatic-deletion policy.
Storage local to a compute node May disappear or become inaccessible when the allocation ends.

Keep the only copy of important inputs and completed results in storage whose retention and backup arrangements you understand. A saved notebook does not contain every separate file its code produces.

1. Connect VS Code to the login node

On your computer, install VS Code. On macOS, move it into Applications; on Windows, run the installer. SSH creates an encrypted connection to another computer; see VS Code’s SSH client instructions if it is not installed.

  1. Choose View → Extensions and install Remote - SSH, published by Microsoft.
  2. Open View → Command Palette, which searches VS Code’s commands, and select Remote-SSH: Add New SSH Host….
  3. Enter the following command with your username and login address, then choose the configuration file in your user folder to save it:
ssh YOUR_USERNAME@LOGIN_HOST

Replace both capitalized values; @ separates your username from the computer’s address. Use your institution’s connection command if it differs. From the Command Palette, choose Remote-SSH: Connect to Host… and select the saved host.

Complete sign-in, checking any first-connection host fingerprint against your institution’s published information. Select Linux if asked for the remote operating system. The new window’s lower-left indicator should show SSH: and the login host. See VS Code’s connection instructions.

In this window, Explorer, saved edits, and new terminals use the cluster. A local project copy remains separate; Remote-SSH does not synchronize it automatically.

Use this window to prepare the project and request resources.

2. Create or open your research project

In the remote VS Code window, choose File → Open Folder and open your approved shared storage location.

For a new project, right-click that folder in Explorer and choose New Folder to create a folder such as memory-project. Open it with File → Open Folder, confirm trust if prompted, then create notebooks, data, and results folders inside it.

If you already have a research project on your computer, transfer its notebooks, required inputs, and environment configuration to this location using the file-transfer instructions below. You can also create and edit notebooks directly on the cluster.

This folder belongs to your research. JAXCMR will be installed into its Python environment.

3. Install the project’s software on the cluster

Open Terminal → New Terminal in the remote project folder. A terminal accepts commands; enter each command and press Return or Enter. Use pwd to print the current folder and check that it is your project.

Python runs the calculations; uv installs Python and the packages the project needs. Check that Git and uv are available:

git --version
uv --version

Git is used to fetch JAXCMR during installation. Use your institution’s software modules or installation instructions if either command is unavailable.

NoteIf Git or uv is unavailable

Some clusters provide software through environment modules. A command such as module load NAME selects an administrator-installed package and adjusts the current terminal so it can find that software. Replace NAME with your institution’s actual module name and version. This selects existing software; uv installs Python packages for your project. Record any required module commands, since new sessions and jobs may need them again. If Git and uv are already available, no extra module is needed. See the Environment Modules documentation.

If your institution provides uv, use that installation. Otherwise, where user installations are permitted, run:

curl -LsSf https://astral.sh/uv/install.sh | sh
source "$HOME/.local/bin/env"

The first command downloads and runs uv’s installer. For its default installation location, the second makes uv available in this terminal: $HOME is your cluster home folder, and source applies settings from the named file. If downloads are restricted, use your institution’s supported installation route.

For a new project

Run:

uv init --bare --python 3.12 --vcs none
uv python pin 3.12
uv add "jaxcmr @ git+https://github.com/githubpsyche/jaxcmr.git@main" ipykernel pandas

These commands create the project’s software configuration, select Python 3.12, and install JAXCMR, notebook support, and table-handling tools. The initialization options keep the starting files minimal and leave version-control setup to you. uv downloads Python if needed and permitted by your cluster.

The installed environment is stored in .venv. The configuration files—pyproject.toml, uv.lock, and .python-version—record what it needs. The local guide explains these files.

For a project transferred from your computer

If you transferred those configuration files from an existing uv project, run:

uv sync --locked

This creates the cluster’s .venv using the recorded dependencies. It checks that the configuration and lockfile agree rather than silently changing the recorded dependency selection. See uv’s locking and syncing guidance.

Create the environment on the cluster even if you already have one locally. Installed environments contain software specific to the computer where they were created.

Wait for installation to finish successfully before continuing.

4. Request computing resources

An interactive allocation gives you temporary resources for commands entered in a terminal. Use your institution’s interactive-access command if it provides one. Otherwise, this is a standard Slurm example, run from the login node with memory-project as the current folder:

srun \
  --account=YOUR_ACCOUNT \
  --partition=YOUR_CPU_PARTITION \
  --nodes=1 \
  --ntasks=1 \
  --cpus-per-task=1 \
  --mem=4G \
  --time=00:30:00 \
  --pty bash

Replace the account and partition. Each backslash continues the same command onto the next line.

Part Meaning
srun Requests resources and starts a program
--account Selects the project allocation
--partition Selects the group of machines
--nodes=1 Uses one compute node
--ntasks=1 Starts one task
--cpus-per-task=1 Allocates one CPU to that task
--mem=4G Requests 4 GB of memory
--time=00:30:00 Limits the session to thirty minutes after it starts
--pty bash Opens an interactive command shell on the allocated node

These values suit a small setup check; adapt them to your cluster’s permitted requests and required options. You may wait for resources. See Slurm’s srun documentation.

Once the session starts, run:

hostname
echo "$SLURM_JOB_ID"

Record the computer name and job number: hostname identifies the allocated node; echo prints the job number stored in SLURM_JOB_ID. Keep this terminal and its VS Code window open. They hold the allocation while you connect a second window to the node.

Only this terminal has moved to the compute node. The original VS Code window and its notebook kernels still belong to the login node.

5. Connect a second window to the compute node

For a managed VS Code service, use its allocated workspace and continue to step 6. For the supported SSH route:

  1. Choose File → New Window to open a local VS Code window. Keep the allocation window open.
  2. In the new window, choose Remote-SSH: Open SSH Configuration File… from the Command Palette. Select the local configuration file used in step 1.
  3. Add this entry before any general Host * entry, replacing the capitalized values. COMPUTE_HOST is the allocated node’s SSH address, usually the name printed above. LOGIN_HOST is the login address or configured alias from step 1.
Host jaxcmr-compute
    HostName COMPUTE_HOST
    User YOUR_USERNAME
    ProxyJump YOUR_USERNAME@LOGIN_HOST

jaxcmr-compute is a convenient connection name. HostName selects the computer, User selects your account, and ProxyJump routes the connection through the login host. Keep any additional authentication settings your institution requires.

Save the file, then use Remote-SSH: Connect to Host… → jaxcmr-compute in this new window. After authentication, its lower-left indicator should show SSH: jaxcmr-compute. Open a new terminal and run hostname; it must match the allocated node, not the login node.

Use File → Open Folder to open the same full memory-project path on shared storage. The files are already there. This second window is now your working window for notebooks.

6. Work with your own notebooks

A Jupyter notebook is an .ipynb file combining explanations, Python code, and results. Its sections are called cells; code cells run in a Python process called a kernel. VS Code’s Jupyter extension supplies the notebook controls.

In the compute window, open View → Extensions and install Microsoft’s Python and Jupyter extensions for SSH: jaxcmr-compute. Use your institution’s supplied extensions if installation is restricted. Open the shared memory-project folder.

Create a notebook through View → Command Palette → Create: New Jupyter Notebook and save it in notebooks with a filename ending in .ipynb. You can also download a JAXCMR notebook through its documentation page and transfer it to notebooks, or use File → Save As to copy an existing notebook. Obtain any separate inputs listed by its instructions; the templates’ automatic example downloads run only in Colab.

Choose Select Kernel → Select Another Kernel → Python Environments and select Python 3.12 from the .venv inside your cluster memory-project folder. If a kernel is already selected, click its name to check or change it.

The notebook controls work as described in Create or download a notebook in the local guide. You can follow that section directly without installing anything on your own computer.

In this window, notebook execution happens on the compute node and saved files belong to the cluster. Selecting an environment in the original login window would run there instead. Keep calculations in the compute window; the login window remains useful for preparing files and managing allocations. See VS Code’s kernel guidance.

NoteOptional: check your installation

Download the first simulation notebook to your computer and transfer it into the cluster project’s notebooks folder. In the compute window, open it, select the project’s .venv, and click Run All. The Colab installation cell skips installation here. The notebook needs no input file; the first calculation may take longer while JAX prepares it.

The final cell should print:

Study order: [1 2 3 4 5]
Simulated recalls: [1 5 2 4 3]

Saved output can be visible before execution, so check that this run finishes without errors. The notebook explains the simulation itself.

7. Move files between your computer and the cluster

Remote SSH does not automatically synchronize local and cluster copies. You can create notebooks directly on the cluster, but inputs already on your computer must be transferred.

Use your institution’s transfer service if it specifies one. Where ordinary SSH file transfers are supported, scp copies files using your SSH sign-in.

On your own computer, open a local VS Code window, use File → Open Folder to open the folder containing your input file, and choose Terminal → New Terminal. Copy a file to the cluster with:

scp "trials.csv" "YOUR_USERNAME@LOGIN_HOST:/FULL/PROJECT/PATH/data/"

Replace trials.csv with your filename, the username and host with your sign-in details, and /FULL/PROJECT/PATH with the cluster’s memory-project location. Obtain that full path with Copy Path in the remote Explorer. Create the destination folder first. The first argument is the source; the second is the destination. The colon separates a remote computer’s address from its file path.

To retrieve a results folder, open the desired destination folder locally, open a new terminal there, and run:

scp -r "YOUR_USERNAME@LOGIN_HOST:/FULL/PROJECT/PATH/results" .

-r copies a folder and its contents; . means the local terminal’s current folder. The same pattern transfers notebooks or other files. Copying can replace matching filenames, and subsequent edits do not synchronize automatically. See the OpenSSH file-copy reference.

Transfer an existing project’s configuration

Use the file-transfer method supported by your institution. Where scp is supported, first create the destination project folder on the cluster.

On your own computer, open the local project folder in VS Code and choose Terminal → New Terminal. Copy its environment configuration with:

scp pyproject.toml uv.lock .python-version "YOUR_USERNAME@LOGIN_HOST:/FULL/PROJECT/PATH/"

Replace the username, login host, and destination with your cluster details. Copy notebooks and inputs using the same method. For the folder arrangement used here:

scp -r notebooks data "YOUR_USERNAME@LOGIN_HOST:/FULL/PROJECT/PATH/"

Transfer existing results too if the cluster work needs them. Recreate .venv using uv sync --locked in the remote project folder.

After transfer, local and cluster copies remain separate. Update full paths in notebook settings to their cluster locations. Copy completed outputs back using the results-transfer instructions above.

8. Use inputs and save outputs

Follow Use your own files and Save results and return later in the local guide, using paths copied from the remote Explorer.

Set the notebook’s project path, or its project_root configuration where present, to the cluster’s memory-project folder. A path pointing to your laptop’s Documents folder will not locate the transferred file. After copying an input, check that it appears in the remote Explorer and that the notebook’s input check prints True.

Save tables, figures, and other outputs to shared storage, using separate filenames or folders for runs you want to preserve. You can reopen these files in another allocation or transfer them to your computer. Saving a result file is what makes it available later; leaving a value in Python’s memory does not.

Finish and return later

Save your notebook and any results you want to retain before ending the allocation. When the allocation’s time limit is reached, its running calculations may be terminated; code that has not yet saved its results cannot be recovered simply by reopening the notebook.

Close the compute connection. In the original allocation terminal, run:

exit

This ends the interactive job and returns that terminal to the login node. Run squeue --jobs=YOUR_JOB_ID, replacing the placeholder with the recorded job number, to check that it has ended. If it remains queued or running, scancel YOUR_JOB_ID cancels that allocation. Closing only the editor window is not a substitute for ending the job.

Your saved files and .venv remain on shared storage according to its retention policy. To return:

  1. Reconnect to the login host and request a new allocation. Load any site-required modules as part of the supported connection procedure.
  2. Update HostName in the existing jaxcmr-compute SSH configuration entry and reconnect the compute window.
  3. Open the same shared project folder and select its .venv.
  4. Run your imports and path settings, then load inputs or saved results.

The environment normally remains available between allocations. If you intentionally transfer updated dependency configuration from another computer, run uv sync --locked before starting notebook kernels. The new session’s Python variables must be recreated by running code. Use Run All when you intend to repeat the whole workflow; otherwise, load saved results and run the subsequent steps you need.

Continue with JAXCMR

Download Preparing data for JAXCMR, transfer it into the cluster project’s notebooks folder, and open it in an allocated compute window. Then use the templates for analysis and modelling. Select the same .venv environment and choose resources appropriate to the work; the setup allocation above is only for a small check.

Once you have a notebook you can run and inspect, follow Run batches of notebooks unattended on Slurm to submit it without keeping an interactive session open, repeat it with different settings, and manage multiple independent jobs.

NoteOptional: work with the JAXCMR checkout

If you need the complete repository or want to modify JAXCMR itself, follow the local guide’s optional cloning instructions in a cluster terminal, using approved shared storage. The existing template tour uses this route.

Keep that checkout separate from your research project. Open its folder and select its own .venv when working on the library or running repository-dependent examples.

If something goes wrong

NoteSSH or VS Code cannot connect

From a local VS Code window, open Terminal → New Terminal and try ssh YOUR_USERNAME@LOGIN_HOST. If ssh is missing, follow the SSH client instructions in step 1. If sign-in fails, check the login address, VPN, and authentication requirements. After a successful terminal test, exit returns to your computer. If SSH works but VS Code does not, inspect View → Output → Remote - SSH.

For the compute connection, confirm that the allocation is still running, HostName names its node, and your institution supports SSH through the login host with your authentication setup. Use its managed service or tunnel procedure where direct SSH is unsupported.

NoteA command is not found

Check which machine the terminal belongs to. On the cluster, confirm that installation completed and load any required software module. For a default uv installation, source "$HOME/.local/bin/env" makes it available in the current terminal.

NoteSlurm rejects the request

Check the account, partition, and permitted resource settings against your allocation. These are cluster access settings, not Python settings.

NoteThe compute node cannot find the project or import JAXCMR

Check pwd, shared storage access, and whether installation finished successfully. Use .venv/bin/python from the intended project folder.

NoteA notebook cannot find an input file

Check that the file was transferred and appears in the remote Explorer. Use Copy Path there to compare its cluster location with the notebook’s settings. A local file path does not refer to the remote copy. Check Path.cwd() inside the notebook if using a relative path.

When asking for help, include the command, complete error message, and whether it ran on your computer, a login node, or a compute node.
